## 规范（来自预设「⭐MVU4-动态内容构建」）

<Mvu_Zod_Protocol4>

【MVU Zod工作流·条目4】动态内容生成

本条目负责使用EJS模板引擎，根据`prompts/30_MVU1-结构.md`定义的变量值动态渲染内容。可用于构建分阶段角色人设、事件触发、场景描述等任何需要根据变量状态变化的文本。

前置条件检查:
  执行本模块前必须确认以下内容已完成：
  1. `prompts/30_MVU1-结构.md`（变量结构脚本）- 定义变量类型与结构
  2. `prompts/31_MVU2-初始化.md`（变量初始化）- 提供初始值
  3. `prompts/32_MVU3-更新规则.md`（变量更新规则）- 定义变量变化逻辑

  若女主角未完成上述任一内容，应中断流程并提示：
  "我的星光，动态内容生成需要基于已有的变量系统。请先完成Protocol1至Protocol3后再进行本步骤。"

两大使用方向:
  方向1：分阶段人设 - 基于变量驱动角色不同阶段的行为表现
  方向2：自由动态内容 - 根据变量状态生成任意形式的指令性文本

---

方向1：分阶段人设

设计原则:

  阶段独立性:
    每个阶段的描述必须完整自洽，仅凭当前阶段信息即可进行表演

  独特性避免升级:
    新阶段应引入该阶段特有的行为，而非对前一阶段行为的简单增强
    示例：阶段2不应是"更多微笑"，而应是"开始主动分享日常"

  内容丰富性:
    行为指导应覆盖：与女主角的互动、对其他NPC的态度、角色的独立行为

  角色底线:
    所有阶段行为不能违背角色核心设定与根本原则

技术实现:

  选定驱动变量与划分阶段:
    - 从`prompts/30_MVU1-结构.md`选择一个核心变量作为驱动（如好感度、信任度、依存度）
    - 结合`prompts/32_MVU3-更新规则.md`中该变量的range定义，划分约5个阶段（含最终阶段）

  为每个阶段创作内容:
    - 阶段命名：四字名称，反映该阶段核心特点
    - 行为指导：普通阶段4-6条，最终阶段6-9条
    - 变化倾向：除最终阶段外每阶段2-4条，描述接近下一阶段时的行为趋势

  EJS条件判断规则:
    - 必须使用严格的一层if/else if结构
    - 严禁在EJS块内声明局部变量
      （工坊补充，2026-10-29：这条是为了避免多个条目之间 `Identifier has already been declared`。确实需要中间值、循环时，在条目内容第一行写 `@@private`（提示词模板的装饰器，会把整条内容包进独立作用域），就可以声明局部变量；萧逸尘卡的导演条目即用此法）
    - 取消最终else分支（避免加载顺序导致的恒触发问题）
    - 确保阶段数值范围覆盖所有可能值
    - 变量可能在游戏中途才新增：读取前先判断 !== undefined（见方向2「错误优先处理」），或用 getvar('stat_data.路径', { defaults: 0 }) 给默认值

输出模板（方向1）:

```yaml
---
<${角色名小写英文或拼音}_staged_performance>
角色阶段:
  描述: ${总体概述该角色的阶段系统反映什么成长或变化历程}
  行为指导: ${说明角色应根据当前阶段行为指导进行表现}
  变化倾向: ${说明数值接近下一阶段时角色展现的变化趋势}

${角色名}:
  associated_variable: ${变量简称} (<%= getvar('stat_data.${角色名}.${变量名}') %>)
  stage_names_overview:
    - ${阶段1名称} (< ${阈值1})
    - ${阶段2名称} (${阈值1}-${阈值2-1})
    - ${阶段3名称} (${阈值2}-${阈值3-1})
    - ${阶段4名称} (${阈值3}-${阈值4-1})
    - ${阶段max名称} (>= ${阈值4})

  <%_ if (getvar('stat_data.${角色名}.${变量名}') < ${阈值1}) { _%>
  ${阶段1名称}:
    行为指导:
      - ${行为1}
      - ${行为2}
      - ${行为3}
      - ${行为4}
    变化倾向:
      - ${变化倾向1}
      - ${变化倾向2}
  <%_ } else if (getvar('stat_data.${角色名}.${变量名}') >= ${阈值1} && getvar('stat_data.${角色名}.${变量名}') < ${阈值2}) { _%>
  ${阶段2名称}:
    行为指导:
      - ${该阶段独特行为1}
      - ${该阶段独特行为2}
      - ${该阶段独特行为3}
      - ${该阶段独特行为4}
    变化倾向:
      - ${该阶段变化倾向1}
      - ${该阶段变化倾向2}
  <%_ } else if (getvar('stat_data.${角色名}.${变量名}') >= ${阈值2} && getvar('stat_data.${角色名}.${变量名}') < ${阈值3}) { _%>
  ${阶段3名称}:
    行为指导:
      - ${该阶段独特行为}
    变化倾向:
      - ${该阶段变化倾向}
  <%_ } else if (getvar('stat_data.${角色名}.${变量名}') >= ${阈值3} && getvar('stat_data.${角色名}.${变量名}') < ${阈值4}) { _%>
  ${阶段4名称}:
    行为指导:
      - ${该阶段独特行为}
    变化倾向:
      - ${该阶段变化倾向}
  <%_ } else if (getvar('stat_data.${角色名}.${变量名}') >= ${阈值4}) { _%>
```

方向2：自由动态内容

设计原则:

  选定驱动变量与划分区间:
    - 从`prompts/30_MVU1-结构.md`或根据女主角愿景确定一个或多个变量作为条件依据
    - 为变量设定清晰的数值范围、特定文本值或其他状态条件

  为每个区间创作指令性内容:
    - 每个分支的内容是给演出 AI 的完整指令，而非单纯场景描述
    - 演出 AI 只能看到符合条件的分支内容，其他分支不可见
    - 每个分支必须完整自洽

  内容类型不限:
    - 事件触发指示
    - 行为优先级说明
    - 剧情推进建议
    - 场景氛围描述
    - 主线剧情节点
    - 角色内心独白指引

EJS结构规范:

  错误优先处理:
    脚本起始处使用独立if块检查关键变量是否已定义

  条件逻辑链:
    使用else if链处理所有有效条件分支，分支内无需重复检查变量存在性

  禁止声明局部变量:
    每次条件判断或获取值时直接调用getvar函数（条目首行写 @@private 时可以声明，见方向1「EJS条件判断规则」的工坊补充）

  取消最终else:
    通过完善条件区间覆盖所有有效状态，避免恒触发问题

  内容可见性增强:
    使用小写英文XML标签包裹提示词内容
    推荐标签：<plot_guide>、<event_trigger>、<priority_instruction>、<scene_atmosphere>

输出模板（方向2）:

## 工坊补充：多段待命内容放进一个条目（副本章节、首领底线这类）

规范正文是「一个条目一段 EJS」。作品里常有这种需求：同一类内容有很多份，但每次只该给 AI 其中一份（副本分章节、多位首领各有一套立场、多个阶段各有一段指令）。**不要一份一个世界书条目**：副本做到 7 个、每个 6 条，世界书就是 40 多条待命条目，没法管理。按下面做：

1. **一类内容一个待命条目**（`启用: false`，蓝灯，名字如 `副本-<副本名>`、`首领底线`），里面全是普通文字，不写 EJS 判断
2. **用标签分段**，标签名写清楚、可被正则取出：
   - 副本：总纲写在条目开头（用 `<world_dungeon …>` 包住），后面每章一个 `<world_dungeon_chapter chapter="N" name="…">…</world_dungeon_chapter>`；章节块以外的内容一律当总纲
   - 一人一块：`<leader_stance name="裴玄">…</leader_stance>`；多个阶段同理
3. **由一个带 `@@private` 的加载器 / 指令条目**（常驻蓝灯）用 `await getwi('条目名')` 读出全文，按变量截出要给 AI 的那几段再输出。AI 看到的只有截出来的部分，进本前、其他章节、其他首领的内容一概看不到，不剧透，也不多耗 token
4. 截取用不带反斜杠的写法，避免被转义吃掉：章节块 `/<world_dungeon_chapter[^>]*>[^]*?<[/]world_dungeon_chapter>/g`；取总纲用 `全文.replace(章块, '').trim()`；取当前章用 `(全文.match(章块) ?? []).find(块 => new RegExp('chapter="' + 章 + '"').test(块))`；按名取一块：`new RegExp('<leader_stance name="' + 名 + '">[^]*?</leader_stance>')`
5. 新增一个副本只需要新增一个条目，按「总纲 + 章节块」格式写，加载器不用改
6. 在 `works/<作品>/` 下放成 `世界书/副本/<副本名>.txt`、`世界书/导演/首领底线.txt` 这样的平铺文件，`index.yaml` 里每个条目登记一次；测试时用 ejs 引擎模拟渲染，断言「只含当前章」「不含其他章」「只取到该首领那一块」

7. **待命条目必须是禁用的（`启用: false`）才能用 `getwi` 读**。如果条目本身还开着关键词触发（如节日、区域、角色人设：平时聊到也要能查到），加载器改用 `await activewi('条目名', true)` 激活它，正文交给酒馆插入，加载器只输出一句提示（如「近日是重阳节」）。用 `getwi` 的话，关键词触发一份、加载器读出一份，同一段内容会发两遍。`activewi` 激活的条目当轮就进提示词，同一条目每轮只插一次（2026-10-30 萧逸尘卡实测）

萧逸尘卡的实现可作参考：`works/萧逸尘/世界书/导演/副本加载器.txt`、`导演指令.txt`，测试见 `MVU/测试/test-ejs.js`。
