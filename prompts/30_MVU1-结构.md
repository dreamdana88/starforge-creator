根据女主角需求生成MVU Zod系统的两个脚本文件

规则:

  基础规范:
  - 库使用: z（Zod）和 _（Lodash）默认可用，禁止重复导入
  - 幂等操作: Schema.parse(Schema.parse(input)) === Schema.parse(input)，谨慎使用z.transform
  - 数字类型: 优先使用z.coerce.number()，其他类型使用基础类型
  - 默认值: 使用z.prefault()而非z.default()，仅在用户要求时添加
  - 约束添加: 仅在用户明确要求时添加范围限制
  - 描述字段: 仅在无字段名解释时使用z.describe()，如record的键类型
  - 类型转换: 除z.coerce.number()外不用其他z.coerce.xxx()，布尔直接z.boolean()
  - prefault连带: 复合类型用了prefault时，其所有字段也要prefault
  - transform限制: 只接收解析后的值，不使用context；z.passthrough、z.strict不存在
  - 特殊字段名（2026-10-29 按源码核对，详见 `references/MVU-现行规则.md`「字段前缀」）:
    - 以 $ 开头 → 硬隐藏：酒馆助手的变量宏把它剔除，AI 看不到也就改不了；脚本、EJS、界面照常读写。真相、后台数据、不想剧透的都用它
    - 以 _ 开头 → 软只读：AI 看得见，「不要改」只是「变量输出格式」条目里的一句提示，MVU 不拦截。需要硬只读时，由脚本在每轮更新后把 _ 字段改回上一轮的值

结构选择优先级（按顺序匹配，命中即停止）:
  1. 动态键+相同值类型 → z.record(z.string().describe('键说明'), valueType)
  2. 固定必需键+相同值类型 → z.record(z.enum(['key1', 'key2', ...]), valueType)
     判定条件：键名预先确定且不可增减，所有键的值类型完全一致
     示例：着装（固定六项，值均为string）→ z.record(z.enum(['上装', '下装', '内衣', '袜子', '鞋子', '饰品']), z.string())
     键可缺省时用 z.partialRecord(z.enum([...]), valueType)
  3. 固定键+不同值类型 → z.object({ key1: type1, key2: type2, ... })
  4. 部分必需+动态可选 → z.intersection(z.object({...}), z.record(...))


  强制禁止:
  - 禁止使用z.array()存储可按名称访问的数据，一律使用z.record()
  - 可清除对象使用.prefault({})而非.optional()

  transform规则:
  - 容错处理: 使用z.transform修正而非.min()/.max()拒绝
  - 放置层级: transform应放在其依赖数据所在的最小闭包层级
    - 若逻辑仅涉及当前对象内部字段 → 放在该对象的transform中
    - 若逻辑需跨对象访问 → 放在包含所有相关对象的最近公共祖先层级
  - 实现方式: 优先使用lodash方法简化代码
    - 对象过滤 → _.pickBy(obj, predicate)
    - 键值操作 → _.entries() / _.fromPairs()
    - 数量限制 → .takeRight(n)保留最新

  语义化结构组织:
  - 变量按归属关系进行层级包裹，而非全部平铺在顶层
  - 示例：物品栏属于主角 → 包裹在主角对象内
  - 结构组织原则：同一实体的属性归入同一对象


输出:
