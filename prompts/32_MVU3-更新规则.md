## 规范（来自预设「⭐MVU3-变量更新与指令集」）

<Mvu_Zod_Protocol3>

【MVU Zod工作流·条目3】变量更新规则与变量输出格式

本条目负责为`prompts/30_MVU1-结构.md`定义的每个变量制定更新触发条件与逻辑，并放入AI在运行时读取变量状态（变量列表）和输出更新指令（变量输出格式）的两条固定条目。

前置条件检查:
  执行本模块前必须确认以下两项已完成：
  1. `prompts/30_MVU1-结构.md`（变量结构脚本）- 定义变量类型与结构
  2. `prompts/31_MVU2-初始化.md`（变量初始化）- 提供初始值参考

  若女主角未提供上述任一内容，应立即中断流程并提示：
  "我的星光，变量更新规则需要基于已有的变量结构来制定。请先完成MVU1（变量结构脚本）与MVU2（变量初始化）后再进行本步骤。"

变量更新规则YAML格式规范:

  基本结构:
    ```yaml
    ---
    变量更新规则:
      ${变量名}:
        type: ${变量类型，string类型省略此字段}
        ${可选字段：format、range、category、value}
        check:
          - ${更新规则1}
          - ${更新规则2}
    ```

  字段说明:
    - type: 变量数据类型
      - string类型省略此字段（默认类型）
      - 基础类型直接书写：number、boolean
      - 复杂类型使用TypeScript定义或Zod Schema（用 |- 字符串块）

    - 可选字段（仅在需要时添加）:
      - format: 字符串格式约束，如 YYYY年MM月DD日、HH:MM
      - range: 数值范围，如 0~100
      - category: 数值分段说明，如 0~30: 陌生人 / 31~60: 熟人
      - value: 字段含义补充说明

    - check: 更新触发条件列表
      - 每条规则独占一行
      - 描述何时触发更新、更新逻辑是什么
      - 保持简练，仅列出关键更新时机

编写原则:

  合并相似规则:
    类型相同、更新逻辑相似的变量可合并，使用占位符表示
    示例：
      - 主角.能力面板.力量/敏捷/体质 → 主角.能力面板.${能力值}
      - 多角色的"对主角评价"字段 → ${角色}.对主角评价

  嵌套同一对象的字段:
    同一对象下的多个字段应嵌套书写，减少token消耗
    示例：主角对象下的"物品栏"和"状态"应嵌套在"主角"映射内

  省略规则:
    - string类型省略type字段
    - 以 _ 开头（软只读，AI 不该改）和以 $ 开头（AI 看不到）的字段不列规则
    - 名称自解释且无特殊规则的变量可省略（如"当前地点"、"当前时间"）
    - 仅在确有必要时添加format、range等可选字段

  规则编写要点:
    - 数值变量：说明增减幅度、触发条件、特殊阈值行为
    - 状态变量：说明状态切换的触发条件
    - 记录型变量：说明新增、删除、修改的触发条件
    - 关联变量：说明与其他变量的联动关系

输出格式:
当女主角请求生成变量更新规则或按`prompts/32_MVU3-更新规则.md`生成内容等愿景时，严格按以下步骤执行：

  第一步：前置检查

  确认女主角已完成`prompts/30_MVU1-结构.md`和`prompts/31_MVU2-初始化.md`。若未完成则中断并提示。

  第二步：生成更新规则内容

  根据Schema结构和变量特性生成YAML格式更新规则，写入 `works/<作品>/世界书/变量/变量更新规则.yaml`（MVU 片段里的「[mvu_update]变量更新规则」条目，蓝灯常驻）：

  ```yaml
  ---
  变量更新规则:
    ${根据变量结构和用户需求生成的更新规则}
  ```

  ${简述规则设计的考量：为何如此设定触发条件、特殊机制说明}

  第三步：放入两条固定条目

  从 `templates/MVU/` 复制 `变量列表.txt`、`变量输出格式.yaml` 到 `世界书/变量/`，内容固定，不要改写。条目已在 MVU 片段里，随卡打包：

  - 变量列表：蓝灯，@D0 或 @D1（放 D2、D3 会夹在两条 AI 回复之间，AI 可能以为数据过时）
    ```
    <status_current_variable>{{format_message_variable::stat_data}}</status_current_variable>
    ```
  - [mvu_update]变量输出格式：蓝灯，@D0。规定AI在回复末尾输出 <UpdateVariable>，里面先写简短分析，再写 JSON Patch 风格的更新指令，操作只有五种：
    - replace：替换已有值
    - delta：数值增减（如好感 +3）
    - insert：新增键，或用 `-` 追加到数组末尾
    - remove：删除
    - move：移动

  条目名里的 [mvu_update]：女主角在 MVU 设置里开了「额外模型解析」（另配一个 API 专门更新变量）时，带这个前缀的条目只发给更新变量的 AI，写剧情的 AI 看不到，省 token、也不干扰剧情；反过来，只想发给写剧情的 AI 的条目（如文风、剧情导演、动态人设），名字前加 [mvu_plot]。没开时两种前缀都不起作用，所有条目照常发送。

变量更新规则示例:

  ```yaml
  ---
  变量更新规则:
    世界:
      日期:
        format: YYYY年MM月DD日
        check:
          - 故事时间推进到新的一天时更新
      时间:
        format: HH:MM (24小时制)
        check:
          - 每次对话或事件后根据实际经历时间更新
          - 场景切换时更新为合理时间
      地点:
        check:
          - 场景切换时立即更新
      近期事件.${事件名}:
        check:
          - 发生重要剧情事件时添加
          - 事件结束或过时后移除

    歧令羽:
      好感度:
        type: number
        range: 0~100 (自动钳位)
        category: |
          0~20: 警惕疏离
          21~45: 逐渐放下戒备
          46~70: 产生信任与好感
          71~90: 难以掩饰的在意
          91~100: 深陷其中
        check:
          - 正面互动增加1~3点，负面互动减少2~5点
          - 重要事件可突破常规变化幅度
          - 好感度70+时开始主动寻找接近主角的机会
      与主角的关系:
        check:
          - 随好感度和剧情发展渐进式更新
          - 关系状态改变应有明确剧情支撑
      当前情绪:
        check:
          - 根据当前剧情和互动内容调整
          - 应符合角色性格特质
      穿着:
        check:
          - 场景切换或新的一天开始时更新
          - 根据场合和天气调整
      身体状态:
        value: 记录伤势、疲劳等身体状况
        check:
          - 发生战斗、劳累等事件后更新
          - 休息或治疗后相应恢复
      对主角的印象.${印象关键词}:
        check:
          - 主角表现出某种特质时添加该印象
          - 印象可能随后续互动修正或加深

    主角:
      物品栏.${物品名}:
        type: |-
          {
            描述: string;
            数量: number;
          }
        check:
          - 获得物品时添加或增加数量
          - 使用或失去物品时减少数量
          - 数量归零时自动移除
      已触发事件:
        type: array
        check:
          - 完成特定剧情节点时添加事件标识
          - 用于判断剧情分支和解锁条件
  ```
